# ТЗ: Доработка витрины сегментации пользователей (mart_user_segments)

## 1. Контекст и проблематика
В текущей реализации таблица `mart_user_segments` содержит статический срез сегментов (одна запись на каждого `uid`). При объединении (JOIN) с исторической таблицей логов (`mart_user_general`) по ключу `uid` возникает **ретроспективное искажение данных**: текущий (или последний) сегмент пользователя присваивается всем его действиям в прошлом.

**Цель:** Перевести таблицу `mart_user_segments` на историчную (динамическую) модель (SCD Type 2 / периодический снэпшот). Это позволит анализировать миграцию пользователей между сегментами и корректно считать исторические метрики в DataLens.

---

## 2. Требования к новой структуре таблицы `mart_user_segments`
Таблица должна представлять собой исторический снимок (снэпшот) состояния пользователя на каждый расчетный период. Гранулярность периодов должна строго совпадать с полем `time_period` в таблице логов.

### 2.1. Схема данных (DDL)
Итоговая таблица должна содержать следующий минимальный набор полей:

| Имя поля | Тип данных | Описание |
| :--- | :--- | :--- |
| `time_period` | `Date` / `String` / `Int` | Временной период (день/неделя/месяц). Тип и формат данных **обязан совпадать** с аналогичным полем в `mart_user_general`. |
| `uid` | `Int` / `String` | Уникальный идентификатор пользователя. |
| `segment` | `String` | Рассчитанный сегмент пользователя на конец данного `time_period`. |

*Первичный ключ новой витрины должен быть составным:* `(uid, time_period)`.

---

## 3. Логика расчета сегментов (Правила)
Сегментация должна пересчитываться для каждого `time_period` на основе накопленных данных (или данных за скользящее окно — в зависимости от утвержденной бизнес-логики) на момент этого периода. 

Базовые метрики для расчета (на момент `time_period`):
*   `total_likes` — общее количество лайков.
*   `organic_likes` — количество лайков, поставленных органическим рекомендациям.
*   `algo_likes` — количество лайков, поставленных алгоритмическим рекомендациям.

**Алгоритм ветвления (CASE WHEN):**

1. **Cold (Холодные):** 
   * Условие: `total_likes < 5`
2. **Explorer (Исследователи):** 
   * Условие: `total_likes >= 5` AND `(organic_likes / total_likes) > 0.7`
3. **Passive (Пассивные):** 
   * Условие: `total_likes >= 5` AND `(algo_likes / total_likes) > 0.7`
4. **Mixed (Смешанные):** 
   * Условие: `total_likes >= 5` и не попали под условия Explorer и Passive (нет выраженного преобладания, соотношение от 30% до 70%).

---

## 4. Ожидаемый результат (Пример данных)

Пользователь `uid = 100` начал пользоваться сервисом в периоде `0`. Сначала он мало взаимодействовал, потом стал ставить лайки органике, а потом перешел на алгоритмические миксы. 

**Как это должно выглядеть в новой витрине:**

| time_period | uid | segment |
| :--- | :--- | :--- |
| 0 | 100 | Cold |
| 1 | 100 | Cold |
| 2 | 100 | Explorer |
| 3 | 100 | Mixed |
| 4 | 100 | Passive |

Вместо одной строки `(100, Passive)` мы получаем полную историю эволюции пользователя.

---

## 5. Требования к интеграции
1. В витрине не должно быть дубликатов по составному ключу `(uid, time_period)`. Если пользователь не проявлял активности в `time_period`, но существовал в системе, строка с его предыдущим сегментом должна пролонгироваться (создаваться) для текущего периода.
2. В DataLens объединение (JOIN) будет перенастроено по двум ключам одновременно:
   * `mart_user_general.uid = mart_user_segments.uid` 
   * `mart_user_general.time_period = mart_user_segments.time_period`
